Hexo 博客自建服务器部署踩坑记录

发表于 2026-07-26 分类于 经验总结 阅读次数： Valine： 990 4 分钟

背景

我的 Hexo 博客一直部署在 GitHub Pages 上，访问速度快但国内偶有不稳定。手头有一台云服务器（47.115.49.75，CentOS + 宝塔面板），想把博客也同步部署上去，实现国内外双线访问。

本文记录配置过程和一些意料之外的坑。

需求

  • 保留 GitHub Pages 部署不变
  • 增加自建服务器同步
  • hexo d 一条命令搞定两边
  • 不需要手动上传文件

方案选择

Hexo 官方支持多种 deployer：

方案 原理 Windows 兼容性
hexo-deployer-rsync 本地 rsync → 远程 rsync over SSH ❌ Windows 无 rsync
hexo-deployer-sftp Node.js ssh2 库直连 SFTP ⚠️ 密钥格式问题
自定义 tar+ssh tar 打包 → SSH pipe → 远端解压 ✅

前两个方案在 Windows 上都遇到了问题，最终选择了第三种方案。

3. 踩坑：rsync 在 Windows 上不可用

hexo-deployer-rsync 会在本地 spawn rsync 进程，但 Git Bash for Windows 默认不包含 rsync：

hexo-deployer-sftp 不需要外部命令，但它依赖 ssh2 这个 Node.js 库。我的密钥是用 ssh-keygen 生成的 OpenSSH 格式（新格式，开头是 -----BEGIN OPENSSH PRIVATE KEY-----），而 ssh2 库只支持老式 PEM 格式。转换后虽然能识别密钥了，但又报 All configured authentication methods failed——ssh2 库的密钥交换算法和服务端不匹配，折腾几次无果后放弃。

4. 最终方案：tar + SSH 管道

原理很简单：

  • tar cf - . 把当前目录打包输出到 stdout
  • | ssh ... "tar xf - -C /dest" 通过 SSH 管道发送到远端，远端 tar 解压到目标目录

优点：

  • 不需要本地或远端 rsync
  • tar 和 ssh 在 Git Bash 中都是原生可用的
  • 一条管道，一个连接，效率高
  • 比 scp -r 快（因为 tar 有合并写入优化）

一些思考

为什么不用宝塔面板的同步功能？

宝塔有 rsync 同步插件，但它面向的是面板内文件管理，和 Hexo 构建流程割裂。我更希望一次 hexo d 解决所有事情，而不是在面板里额外配置定时同步。

tar+ssh 和 rsync 比怎么样？

  • rsync 的优势在于增量同步（只传变化的部分），大站点差距明显
  • 我的博客 160 个文件 ~10MB，全量 tar 打包上传在 1-2 秒内完成，增量优化的收益不大
  • 如果以后站点变大，可以在服务器上装 rsync，本地用 ssh user@host "rsync ..." 的方式间接使用

密钥格式的教训

Windows 上用 ssh-keygen 默认生成的是 OpenSSH 格式，但很多 Node.js 的 SSH 库（ssh2、node-ssh 等）只支持 PEM 格式。如果需要在新旧格式间转换：
